# Mini B2B RFQ Marketplace

A two-sided marketplace where **buyers** post procurement requirements (RFQs) and **suppliers**
discover them and submit quotations. Buyers compare the quotes they receive and award the RFQ to
one supplier.

## Technology stack

| Layer    | Choice                                    | Why                                                                                                            |
| -------- | ----------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| Backend  | Python 3.11, FastAPI                      | Request/response validation comes from the type hints, and the OpenAPI docs are generated rather than maintained. |
| ORM      | SQLAlchemy 2.0 (typed `Mapped[...]` style) | Constraints live next to the models, so the schema and the code cannot drift apart.                              |
| Database | PostgreSQL in production, SQLite locally  | Identical SQL through the ORM; zero setup to run the project locally or in CI.                                    |
| Auth     | JWT (PyJWT) + bcrypt                      | Stateless tokens, so the API scales horizontally with no shared session store.                                    |
| Frontend | React 18 + Vite + React Router 6          | Fast builds, no framework beyond what a SPA of this size needs.                                                  |
| Styling  | Hand-written CSS with custom properties   | One 700-line stylesheet, no build step or utility framework to explain.                                           |
| Tests    | pytest + FastAPI `TestClient`             | 50 tests covering auth, permissions and every business rule.                                                     |

## Running it locally

### 1. Backend

```bash
cd backend
python -m venv .venv && source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt

cp .env.example .env        # optional — defaults to SQLite, which needs no setup
python seed.py              # creates the demo accounts and sample RFQs
uvicorn app.main:app --reload
```

The API is now on `http://localhost:8000`, with interactive docs at `http://localhost:8000/docs`.

### 2. Frontend

In a second terminal:

```bash
cd frontend
npm install
npm run dev
```

Open `http://localhost:5173`. The dev server talks to `http://localhost:8000` by default; override
with `VITE_API_URL` in `frontend/.env` if your API runs elsewhere.

### 3. Tests

```bash
cd backend
pytest -q       # 50 passed
```

## Architecture

```
┌──────────────────────┐        JSON over HTTPS         ┌────────────────────────┐
│  React SPA (Vite)    │  ───────────────────────────►  │  FastAPI               │
│                      │      Authorization: Bearer     │                        │
│  • AuthContext       │  ◄───────────────────────────  │  routers/  auth        │
│  • api.js (1 fetch   │                                │            rfqs        │
│    wrapper)          │                                │            quotations  │
│  • Protected routes  │                                │  deps.py   authn/authz │
└──────────────────────┘                                │  schemas.py validation │
                                                        │  models.py  ORM        │
                                                        └───────────┬────────────┘
                                                                    │ SQLAlchemy
                                                                    ▼
                                                        ┌────────────────────────┐
                                                        │ PostgreSQL             │
                                                        │ users / rfqs /         │
                                                        │ quotations             │
                                                        └────────────────────────┘
```

### Backend layering

Each module has one job, so a change has one obvious home:

- **`models.py`** — tables, relationships and database-level constraints.
- **`schemas.py`** — the validation boundary. Anything reaching a handler is already type-checked
  and range-checked. Response schemas double as a field whitelist: `password_hash` is not declared
  in `UserOut`, so it cannot leak even by accident.
- **`deps.py`** — `get_current_user`, `require_buyer`, `require_supplier`. Authorization is declared
  in the route signature, so a new endpoint cannot silently forget it.
- **`routers/`** — HTTP handling and business rules only.
- **`security.py`** — hashing and token logic, isolated so it can be swapped without touching routes.

### Frontend structure

- **`lib/api.js`** — every network call goes through one `request()`. The bearer header, JSON
  encoding and error shape are defined once. A 401 clears the stored token so the router redirects
  to login on the next render.
- **`lib/auth.jsx`** — on load, the app asks `/api/auth/me` whether the stored token is still valid
  rather than trusting a cached user object.
- **`components/Protected.jsx`** — route guards. These are a **UX** convenience; the real
  enforcement is server-side.
- **`components/States.jsx`** — shared `Loading` / `Empty` / `ErrorState`, so no screen renders
  blank while fetching or dead-ends on an error.

## Data model

```
users                          rfqs                            quotations
─────                          ────                            ──────────
id            PK               id               PK             id             PK
name                           buyer_id      FK→users.id       rfq_id      FK→rfqs.id
email         UNIQUE, indexed  title                           supplier_id FK→users.id
password_hash                  description                     price          NUMERIC(12,2)
role          buyer|supplier   quantity      CHECK > 0         delivery_days  CHECK > 0
company_name                   unit                            notes
created_at                     delivery_location               status  pending|accepted|rejected
                               deadline      DATE              created_at / updated_at
                               status  open|closed|awarded
                               created_at / updated_at         UNIQUE (rfq_id, supplier_id)
                               INDEX (status, deadline)
```

Decisions worth calling out:

- **`UNIQUE (rfq_id, supplier_id)`** — a supplier gets exactly one live quote per RFQ. Re-submitting
  updates the existing row instead of creating a duplicate. The constraint is in the database, not
  just in application code, so two concurrent requests cannot both slip through.
- **`NUMERIC(12,2)` for price, never `FLOAT`** — binary floating point cannot represent `0.10`
  exactly, and rounding drift in money is a real bug.
- **Composite index on `(status, deadline)`** — the supplier browse query filters on both columns on
  every request; this is the one query guaranteed to run constantly.
- **Enums stored as `VARCHAR` + `CHECK`, not native Postgres `ENUM`** — the same DDL works on SQLite
  for local dev and tests, and adding a status later is an ordinary constraint change rather than an
  `ALTER TYPE` that locks the table.
- **One role per account.** A user is a buyer or a supplier, never both. This makes every
  authorization check unambiguous. A real marketplace would likely need organisations with
  per-user roles; that is a larger model than this scope calls for.

## API

All routes except register/login require `Authorization: Bearer <token>`.

| Method   | Endpoint                      | Who         | Purpose                                   |
| -------- | ----------------------------- | ----------- | ----------------------------------------- |
| `POST`   | `/api/auth/register`          | public      | Create an account, returns a token        |
| `POST`   | `/api/auth/login`             | public      | Exchange credentials for a token          |
| `GET`    | `/api/auth/me`                | any         | Current user (used to validate the token) |
| `POST`   | `/api/rfqs`                   | buyer       | Create an RFQ                             |
| `GET`    | `/api/rfqs`                   | any         | Browse open RFQs — search, filter, page   |
| `GET`    | `/api/rfqs/mine`              | buyer       | The buyer's own RFQs                      |
| `GET`    | `/api/rfqs/{id}`              | any         | RFQ detail                                |
| `PATCH`  | `/api/rfqs/{id}`              | buyer/owner | Update an RFQ                             |
| `DELETE` | `/api/rfqs/{id}`              | buyer/owner | Delete (only while it has no quotes)      |
| `POST`   | `/api/rfqs/{id}/quotations`   | supplier    | Submit or revise a quotation              |
| `GET`    | `/api/rfqs/{id}/quotations`   | buyer/owner | All quotes on that RFQ, cheapest first    |
| `GET`    | `/api/quotations/mine`        | supplier    | The supplier's own quotations             |
| `POST`   | `/api/quotations/{id}/accept` | buyer/owner | Award the RFQ to one supplier             |
| `GET`    | `/api/health`                 | public      | Health check for the platform             |

Query parameters on `GET /api/rfqs`: `q`, `location`, `status`, `include_expired`, `sort`
(`newest` \| `deadline`), `page`, `page_size`.

### Status codes

`200` ok · `201` created · `204` deleted · `400` bad request · `401` not authenticated ·
`403` wrong role · `404` not found (or not yours) · `409` conflicts with current state ·
`422` validation failed.

## Business rules

These are the decisions that make it a marketplace rather than a CRUD app. All are enforced
server-side; the UI mirrors them for a better experience but is never the thing being trusted.

1. **Quotes are frozen after the deadline or once the RFQ is closed or awarded.** Checked on the
   server on every submission.
2. **One quote per supplier per RFQ.** Re-submitting revises it. Enforced by a unique constraint.
3. **Commercial terms freeze once the first quote arrives.** A buyer cannot change quantity, title
   or delivery location after suppliers have priced the work — nobody should bid against a moving
   target. Description and deadline stay editable so a buyer can still clarify, and the deadline can
   only be *extended*, never shortened.
4. **Accepting is atomic.** One transaction marks the winner accepted, rejects every sibling and
   moves the RFQ to `awarded`. There is no window where two quotes both look accepted.
5. **An RFQ with quotations cannot be deleted**, only closed. Suppliers have invested effort and
   deserve a record of it.
6. **Suppliers never see each other's prices.** A supplier can only read their own quotations.
7. **An awarded RFQ cannot be awarded again**, and losing suppliers cannot undercut afterwards.

## Security

- **Passwords** are bcrypt-hashed with a per-password salt. Plaintext is never stored or logged.
  Input longer than bcrypt's 72-byte limit is rejected rather than silently truncated, so a hash can
  never depend on ignored characters.
- **Login is uniform.** An unknown email and a wrong password return the identical status and
  message, so the endpoint cannot be used to enumerate which addresses are registered.
- **Authorization is a route dependency**, not an `if` inside a handler — it cannot be forgotten on
  a new endpoint.
- **404, not 403, for another user's resources.** Returning 403 would confirm that a given id
  exists; 404 reveals nothing.
- **Response schemas whitelist fields.** Suppliers browsing RFQs see the buyer's name and company,
  never their email address.
- **Errors never leak internals.** Unhandled exceptions are logged in full server-side and returned
  to the client as a generic message — no stack traces, table names or library versions.
- **The app refuses to boot in production with the default dev JWT secret.** Failing loudly beats
  running with decorative auth.
- **SQL injection** is not reachable: every query goes through SQLAlchemy's parameter binding.
- **CORS** is an explicit origin allowlist, not `*`.

## Testing

50 tests in `backend/tests/`, run with `pytest -q`. Each test gets its own in-memory SQLite
database, so they are isolated and order-independent.

| File                  | Covers                                                                            |
| --------------------- | --------------------------------------------------------------------------------- |
| `test_auth.py`        | Registration, duplicate and case-folded emails, weak passwords, login, enumeration resistance, token rejection |
| `test_rfqs.py`        | Creation, role enforcement, validation, search, filtering, pagination, ownership, the edit-freeze rule, delete guards |
| `test_quotations.py`  | Submission, revision, deadline and status guards, buyer/supplier visibility isolation, the award transaction |

The suite deliberately leans on the failure cases — the tests that matter are the ones asserting
that the wrong person gets a 403 or a 404.

## Deployment

The frontend is a static bundle and the backend is a single ASGI process, so they deploy
independently.

### Backend (Render, Railway, Fly.io, or any container host)

1. Provision a PostgreSQL database and copy its connection string.
2. Create a web service from this repo with root directory `backend`.
   - **Build:** `pip install -r requirements.txt`
   - **Start:** `uvicorn app.main:app --host 0.0.0.0 --port $PORT`
3. Set environment variables:

   | Variable        | Value                                                                   |
   | --------------- | ----------------------------------------------------------------------- |
   | `DATABASE_URL`  | `postgresql+psycopg://…` (add the `+psycopg` driver prefix)              |
   | `JWT_SECRET`    | `python -c "import secrets; print(secrets.token_urlsafe(48))"`          |
   | `CORS_ORIGINS`  | your deployed frontend URL, e.g. `https://your-app.vercel.app`           |
   | `ENVIRONMENT`   | `production`                                                            |

4. Optionally run `python seed.py` once to load the demo data.

`render.yaml` in the repo root captures this as infrastructure-as-code.

### Frontend (Vercel, Netlify, or any static host)

1. Import the repo, set root directory `frontend`.
   - **Build:** `npm run build` · **Output:** `dist`
2. Set `VITE_API_URL` to your deployed backend URL.
3. Redeploy so the variable is baked into the bundle — Vite inlines env vars at build time, so
   changing it later requires a rebuild, not just a restart.

> **The most common deployment mistake here is CORS.** `CORS_ORIGINS` on the backend must exactly
> match the frontend's scheme and host, with no trailing slash. A mismatch shows up as
> "Cannot reach the server" in the UI and a CORS error in the browser console, even though the API
> itself is healthy.

`vercel.json` includes the SPA rewrite so deep links like `/buyer/rfqs/3` resolve to `index.html`
instead of 404ing.

## Assumptions

1. **One role per account**, chosen at signup. See the data model section for why.
2. **Single currency (INR).** Prices are stored as a plain decimal with no currency column. A real
   cross-border marketplace would need one.
3. **Deadlines are dates, not timestamps**, interpreted in the server's timezone. Precise enough for
   procurement; a global marketplace would want timezone-aware instants.
4. **No file attachments.** Real RFQs carry drawings and spec sheets; that needs object storage and
   was out of scope here.
5. **No email notifications.** A supplier learns their quote was accepted by opening the app.
6. **Quote revision is allowed** while the quote is still pending. This seemed more realistic than
   forcing a supplier to live with a typo, and the audit trail (`updated_at`) records that it changed.
7. **Seed data is Indian B2B procurement** — it needed to be something concrete, and the formatting
   helpers use the `en-IN` locale to match.

## Limitations, and what I would do next

- **Schema is created with `create_all()` at startup, not migrations.** Correct for a project this
  size; the first thing I would add for a real deployment is Alembic, so schema changes are
  versioned and reversible.
- **JWTs cannot be revoked before expiry.** Logging out clears the token client-side, but a stolen
  token stays valid for its lifetime. A refresh-token pair with a server-side denylist is the fix.
- **Tokens are kept in `localStorage`**, which is readable by any script running on the page. That
  is the standard trade-off for a SPA on a separate origin; the more secure option is an
  `httpOnly`, `SameSite=Strict` cookie, which needs the API and frontend to share a domain.
- **No rate limiting on login.** In production this belongs at the edge (the platform's WAF) or as
  middleware, to blunt credential-stuffing.
- **Pagination is offset-based.** Fine at this scale; cursor pagination is better once the table is
  large, because `OFFSET 10000` still scans the rows it skips.
- **No frontend tests.** The backend rules are well covered; component and end-to-end tests
  (Vitest + Playwright) would be the next addition.
- **Browse is not full-text search.** `ILIKE '%term%'` cannot use a normal index. Postgres
  `tsvector` with a GIN index is the upgrade once the RFQ table grows.
